Title of the ProjectWhen and What to Retrieve: Adaptive Temporal Retrieval-Augmented Generation for Time-Aware Question Answering (Adaptive Temporal RAG).Short title used in implementation and demo: Adaptive Temporal RAG — a framework that decides whether retrieval is needed and which temporal ranking policy to apply for time-sensitive question answering.2. IntroductionLarge Language Models (LLMs) perform well on many language tasks, but their parameters are frozen after training. They cannot natively track facts that change after the training cut-off and may produce outdated or fabricated answers for time-sensitive questions.Retrieval-Augmented Generation (RAG) mitigates this by fetching external documents at query time and supplying them as context to the generator. Conventional RAG ranks passages almost exclusively by semantic similarity. That is insufficient when the correct evidence depends on time: “current” facts need recent documents; historical questions need evidence near a target year; timeless questions may need no retrieval at all.This minor project designs, implements, and evaluates Adaptive Temporal RAG: a DistilBERT multitask query analyzer predicts retrieval necessity, temporal class (current / historical / timeless), and confidence; a policy module then selects no-retrieval, recency ranking, historical windowing, or semantic-only fallback. The system is compared against LLM-only, Standard RAG, and Fixed Temporal RAG baselines on a curated dated corpus.3. Literature Survey3.1 Foundational Retrieval-Augmented GenerationLewis et al. (2020) introduced RAG by combining dense retrieval with sequence-to-sequence generation, improving factual accuracy on knowledge-intensive tasks. Dense Passage Retrieval (Karpukhin et al., 2020) showed that learned embeddings often outperform sparse lexical retrieval. Fusion-in-Decoder (Izacard & Grave, 2021) improved how multiple passages are fused during generation. These systems form the semantic-similarity baseline of this project (Standard RAG).3.2 Temporal and Freshness-Aware RetrievalFreshLLM / FreshQA-style evaluations (Vu et al., 2023) show that LLMs and standard RAG frequently fail on fast-changing facts unless retrieval favours recent, high-quality sources. Temporal RAG variants incorporate document timestamps into filtering or re-ranking relative to the time referenced by the query. Such methods motivate the Fixed Temporal RAG baseline in this work, but typically apply one temporal rule uniformly to every query.3.3 Adaptive / Selective RetrievalSelf-RAG (Asai et al., 2023) learns when to retrieve and how to critique evidence. Adaptive-RAG (Jeong et al., 2024) routes queries by complexity to no-retrieval, single-step, or multi-step pipelines. FLARE (Jiang et al., 2023) triggers retrieval when generation confidence drops. These methods address whether to retrieve, but not jointly with temporal intent (present vs past vs timeless).3.4 Research GapPrior adaptive systems decide if retrieval is needed; prior temporal systems decide how to weight time after retrieval is already triggered. Few systems jointly estimate retrieval necessity, temporal category, and decision confidence in one query-conditioned policy. Adaptive Temporal RAG targets exactly this gap.4. Problem StatementConventional RAG retrieves primarily by semantic similarity and assumes similar retrieval behaviour for all queries. For time-sensitive information needs this causes: (i) outdated answers when older but similar documents outrank recent ones; (ii) wrong historical answers when the most recent similar document describes a different period; (iii) unnecessary retrieval for timeless/trivial queries; and (iv) avoidable latency and cost.Problem addressed: How can a RAG system automatically detect whether retrieval is necessary and what temporal intent a query carries, then select a query-specific retrieval and ranking strategy that improves temporal correctness and reduces unnecessary retrieval without degrading answer quality?5. MotivationPractical motivation. Assistants are routinely asked current-event and office-holder questions; silently wrong answers erode trust. Retrieval is not free—skipping it when unnecessary reduces latency and cost. Enterprise corpora (news, filings, policies) are timestamped, yet metadata is rarely used beyond crude filters.Research motivation. Temporal reasoning remains a known weakness of LLMs and RAG stacks. Combining retrieval-necessity detection with temporal-intent detection under a confidence-aware policy is a focused, evaluable contribution suitable for a semester minor project, with clear baselines and metrics.6. Proposed Design FlowThis section presents the design flow through two architectures: (A) Temporal RAG — the fixed temporal baseline used for comparison; and (B) Adaptive Temporal RAG — the proposed system. Both share the same dated corpus, MiniLM embeddings, FAISS index, and generator interface so differences are attributable to policy design.6.1 Architecture A — Temporal RAG (Fixed Temporal Baseline)Temporal RAG always retrieves. The query is embedded with Sentence-Transformers MiniLM; FAISS returns a wide candidate set. A fixed rule then applies: if a year is detected in the query (or time hint), candidates are filtered to a ±2-year window and re-ranked for historical proximity; otherwise candidates receive a recency boost. Final ranking uses α·semantic + (1−α)·temporal (default α = 0.6). Top-k passages are passed to the generator. There is no query analyzer and no option to skip retrieval./Figure 1. Temporal RAG architecture (always retrieve + fixed temporal policy).Design flow summary (Temporal RAG):Input query → MiniLM embedding → FAISS candidate retrieval (always).If year present → historical window filter (±2 years) → historical temporal re-rank.Else → recency-based temporal re-rank.Score fusion → top-k evidence → LLM / extractive generator → answer.6.2 Architecture B — Adaptive Temporal RAG (Proposed System)Adaptive Temporal RAG inserts a DistilBERT multitask query analyzer before retrieval. The analyzer predicts: (1) retrieval necessity (0/1); (2) temporal class — current, historical, or timeless; (3) confidence. A policy module then selects: no retrieval (parametric answer); current → recency re-rank; historical → year-window filter then historical re-rank; timeless or low confidence → safer semantic-only ranking. When retrieving, MiniLM + FAISS produce candidates (≈50), which are re-ranked to top-k (default 5) before generation./Figure 2. Proposed Methodology7.1 DatasetA synthetic educational corpus of approximately 800 short dated passages covers politics, business leadership, sports, awards, laws, and timeless encyclopedia facts. High-churn entities appear at multiple timestamps so that historical vs current ranking differs. About 1050 labelled queries include needs_retrieval, temporal_class, optional time_hint, gold_answer, and gold_doc_ids, split 70/15/15 with train paraphrases. Approximate balance: ~35% current / ~30% historical / ~30% timeless; ~25% no-retrieval.7.2 Indexing and BaselinesDocuments are embedded with sentence-transformers/all-MiniLM-L6-v2 and indexed in FAISS IndexFlatIP. Four systems share the same index and generator interface: B1 LLM-only (never retrieve); B2 Standard RAG (always semantic top-k); B3 Fixed Temporal RAG (architecture in §6.1); Proposed Adaptive Temporal RAG (architecture in §6.2).7.3 Query Analyzer TrainingA DistilBERT encoder with three heads (necessity, temporal class, confidence) is fine-tuned on the labelled train split. Loss combines cross-entropy for necessity and temporal class with a confidence term. Best validation checkpoint (necessity F1 and temporal accuracy) is saved to artifacts for inference in the adaptive pipeline and demo.7.4 Temporal ScoringFor current mode, newer documents receive higher temporal affinity (age mapped over ~10 years). For historical mode, affinity peaks near the query year. Semantic and temporal scores are fused with α = 0.6. A fixed reference date (2025-10-01) keeps evaluation reproducible.7.5 Generation and EvaluationThe generator facade supports extractive stub (fast offline eval), local HF LLMs, or API LLMs. Metrics include answer contains / EM / token-F1, temporal accuracy (top-1 evidence date heuristic), precision@k / recall@k, latency, and retrieval rate. A Streamlit app exposes system toggle, α, and confidence threshold for demonstration.8.
